# Frontend Design Brief — evosim Showcase Site

**Audience of this document:** frontend design team
**Status:** draft for discussion · 2026-08-07
**Repo:** https://github.com/aifriend/evosim

---

## 1. Project overview

**evosim** is an open-source reinforcement-learning project that trains
embodied AI agents — simulated bodies (walkers, hoppers, humanoids) and
bodies acting on objects (grippers manipulating cubes) — using Gymnasium,
MuJoCo physics, and Stable Baselines3.

We need a public-facing showcase site that makes the project tangible in
under 10 seconds: a visitor should immediately *see* the agents moving,
understand what each simulation is, and grasp the difference between an
untrained and a trained policy.

A working static prototype exists in `frontend/` (vanilla HTML/CSS/JS, no
build step). The design team is invited to replace its look & feel; the
data contract (§5) and asset pipeline (§6) should survive any redesign.

## 2. Goals

- **Primary:** present every simulation as a living artifact — autoplaying
  video, not screenshots.
- Communicate the two pillars of the project at a glance:
  *locomotion* (bodily agents) and *manipulation* (bodily objects).
- Show honest progress: each card states which policy produced the footage
  (`PPO`, `SAC`, or `random (untrained)`) and the measured mean return.
- Drive visitors to the GitHub repo.

## 3. Non-goals

- No live in-browser simulation (no WebAssembly MuJoCo) in v1 — videos only.
- No accounts, no backend, no database.
- No training dashboard (TensorBoard already covers that for engineers).

## 4. Audience

- ML engineers evaluating the project (want metrics, reproducibility links).
- Students learning RL (want plain-language descriptions).
- Casual visitors from social media (want motion and wow-factor).

## 5. Content & data contract

The site renders whatever the pipeline exports. Today: 8 environments
(CartPole, GripperCube, Reacher, HalfCheetah, Hopper, Walker2d, Ant,
Humanoid). The manifest is `frontend/data/sims.js`:

```js
window.SIMS = [{
  "id": "HalfCheetah-v5",        // display name
  "slug": "halfcheetah",         // url-safe key
  "kind": "locomotion",          // "locomotion" | "manipulation" | "classic control"
  "description": "...",          // 1–2 plain-language sentences
  "video": "data/videos/halfcheetah.mp4",  // square-ish mp4, < 1.5 MB
  "policy": "PPO",               // or "random (untrained)"
  "meanReturn": 1523.4,          // measured over eval episodes
  "evalEpisodes": 3
}]
```

Design must handle: any number of entries, both policies (styled
differently — untrained footage should read as "before"), and kind-based
filtering or grouping (locomotion vs manipulation is the story).

## 6. Technical constraints

- **Static hosting** (GitHub Pages). No server-side anything.
- Assets are generated by `scripts/export_showcase.py`; videos land in
  `frontend/data/videos/`. The pipeline is re-run after every training
  milestone, so the design must tolerate content churn.
- Videos are H.264 mp4, 480×480 (MuJoCo) or 600×400 (classic control),
  muted, loopable, ≤ ~1.5 MB each.
- Prototype stack: vanilla HTML/CSS/JS with a `<dialog>` detail view and
  play-on-hover cards. Feel free to keep or replace — but if a framework
  is introduced, it must still export to static files.

## 7. Pages / views

1. **Gallery (home)** — hero with one-line pitch + GitHub link; responsive
   grid of simulation cards (video, name, kind badge, policy + score).
2. **Detail view** — larger video, full description, stats block
   (policy, mean return, eval episodes). Modal or per-slug page;
   per-slug URLs would make individual sims shareable.
3. *(v2, optional)* — training curves per env, before/after comparisons,
   "how it works" section.

## 8. Design direction (open to proposals)

- Dark, technical, calm — the videos are the color.
- Motion should come from the simulations themselves; keep UI animation
  minimal.
- Typography-led hero; monospace accents fit the subject matter.
- Accessibility: keyboard-navigable cards/dialogs, captions for stats,
  respect `prefers-reduced-motion` (disable autoplay).

## 9. Deliverables we need from the team

1. Visual direction (1–2 moodboard options).
2. High-fidelity mockups: gallery + detail, desktop and mobile.
3. Implemented frontend replacing `frontend/` (or a design system +
   handoff if implementation stays on our side).

## 10. Open questions

- Branding: keep the name "evosim"? Logo needed?
